## Project explanation script

“I built a full-stack Job Portal that connects candidates and recruiters in one platform. The main idea was to reduce manual profile filling and make the job application process faster. Instead of asking users to type their details again and again, the system lets them upload a resume and automatically extracts useful information like skills, contact details, and basic profile data.

Technically, the project is split into three parts. The frontend is built with React, Vite, and Tailwind CSS for a fast and clean user interface. The backend is built with Node.js and Express, which handles authentication, user management, job-related APIs, and real-time messaging. For the resume parsing part, I used a separate Python service with FastAPI because PDF processing and text extraction are more suitable there than inside the Node event loop. That keeps the main backend responsive, especially when multiple users are active at the same time.

When a user uploads a resume, the file is sent from the React frontend to the Express server. The backend temporarily stores the file, forwards it to the Python parsing service, and the parser extracts text from the PDF. Then it looks for important information like email, phone number, and matching skills using pattern-based extraction. After that, the backend saves the profile data in MongoDB and stores the resume file in cloud storage so it can be accessed later. I also added real-time chat using Socket.io so candidates and recruiters can communicate instantly.

One important part of the project was separating responsibilities properly. I did not want heavy PDF parsing to slow down login, chat, or job browsing. That is why I used a microservice-style structure. Another important design choice was MongoDB, because the data is semi-structured. Candidate profiles, job posts, applications, and chat messages all have flexible fields, so MongoDB fits better than forcing everything into fixed relational tables.

The biggest things I learned from this project were deployment, CORS handling, and real-world integration between multiple services. Since the repo is a monorepo, I had to think carefully about deployment paths and build configuration. I also had to handle production issues like file path casing, cross-origin communication, and keeping the socket-based chat secure.

Overall, this project shows that I can build a complete product end to end: frontend, backend, database, file handling, real-time communication, and separate processing for CPU-heavy tasks. It also shows that I understand not just coding features, but the reasoning behind architecture choices.”

## Very likely interviewer questions and answers

### 1) Why did you split the backend into Node.js and Python?

“Because the backend has two different kinds of work. Node.js is good for request handling, authentication, and real-time socket communication. Python is better for PDF text extraction and parsing. If I had done heavy parsing inside Node, it could have blocked the event loop and slowed down other users.”

### 2) Why did you use MongoDB?

“Because the data is flexible. User profiles, skills, job descriptions, and applications do not always fit neatly into strict tables. MongoDB lets me store nested and changing structures more naturally.”

### 3) How does resume parsing work?

“The user uploads a PDF, the backend forwards it to the parser, the Python service extracts text, and then the system identifies important fields using regex and keyword matching. The extracted data is then merged into the user profile.”

### 4) Is this really AI?

“Not in the deep-learning sense. The current parser is rule-based and uses regex and keyword matching. I would describe it honestly as automated resume parsing. The architecture is ready for future upgrades to NLP or LLM-based extraction.”

### 5) Why not do everything in Express?

“Because PDF parsing is CPU-heavy. Express is best when it stays focused on I/O and routing. Mixing heavy parsing into the same process would make the app slower and less stable.”

### 6) How is chat implemented?

“I used Socket.io for real-time messaging. It allows instant message exchange between users without waiting for page refresh or repeated HTTP polling.”

### 7) How do you store chat messages?

“Messages are saved in MongoDB so chat history persists even after refresh or logout. Socket.io is only for real-time delivery; MongoDB keeps the permanent record.”

### 8) What was the hardest issue you solved?

“Deployment and cross-service communication. Since the project is split across frontend, backend, and parsing service, I had to handle CORS, build paths, and environment-specific issues like file path casing.”

### 9) What would you improve next?

“I would make resume parsing asynchronous using a job queue like BullMQ or Celery, add stronger resume understanding with NLP, and improve search and matching with better ranking logic.”

### 10) Why is your project useful?

“Because it saves time for both candidates and recruiters. Candidates do not need to manually type everything from their resume, and recruiters get a faster way to interact and shortlist people.”

Challenge 1: Node.js Event Loop Blocking & Microservice Separation
Q1. Why didn't you perform PDF parsing directly in Node.js?

Answer:

Initially I considered parsing the PDF directly in the Express backend because it would have been simpler. But PDF extraction is CPU-intensive. Since Node.js runs on a single-threaded event loop, long-running CPU tasks block other incoming requests. That means while one user uploads a resume, other users might experience delayed API responses or chat messages.

To avoid that, I separated the parsing logic into a FastAPI microservice written in Python. Express only forwards the file and waits asynchronously for the response, while continuing to handle other requests.

Q2. How did you know the event loop was getting blocked?

Answer:

During testing I uploaded multiple resumes simultaneously while another user was using the chat feature. I noticed API responses became slow and chat messages were delayed. Since PDF parsing is CPU-heavy, it became clear that running it inside Node wasn't scalable.

That led me to move the parsing service into a separate Python process.

Q3. Why did you choose Python instead of another Node library?

Answer:

Python has a much stronger ecosystem for document processing and NLP. Libraries like PDFMiner, PyMuPDF and spaCy are much more mature than most Node alternatives.

Since I already wanted a dedicated parsing service, Python became the natural choice.

Q4. Couldn't Worker Threads solve this?

Answer:

Yes, Worker Threads are another solution. They would work if the entire project stayed inside Node.js.

I preferred a microservice because it completely isolates the parsing service. It can later be upgraded independently with OCR, spaCy or transformer models without changing the Express backend.

Challenge 2: Real-Time Chat Synchronization
Q5. How did you ensure chat messages aren't lost?

Answer:

Socket.io only delivers messages in real time. It doesn't permanently store them.

So whenever a message is sent, the backend first stores it in MongoDB and then emits it through Socket.io.

When a user reconnects or refreshes the page, the frontend requests the complete chat history from MongoDB before opening the socket connection.

Q6. Why didn't you keep everything inside Redux?

Answer:

Redux only stores data in browser memory.

Once the page refreshes, that state disappears.

MongoDB acts as the source of truth while Redux only maintains the current UI state.

Q7. What happens if the user disconnects?

Answer:

Since every message is stored in MongoDB before broadcasting, nothing is lost.

After reconnecting, the client fetches all previous messages and the conversation continues normally.

Q8. Why use Socket.io instead of polling?

Answer:

Polling repeatedly sends HTTP requests even when there are no new messages.

Socket.io keeps a persistent connection so the server pushes new messages instantly.

This reduces unnecessary network traffic and provides a much better user experience.

Challenge 3: Secure Socket Communication
Q9. Why wasn't your first implementation secure?

Answer:

Initially I trusted the client to send its own user ID while joining a room.

During testing I realized anyone could manually emit another user's ID from the browser console and join their room.

That exposed private conversations.

Q10. How did you fix it?

Answer:

Instead of trusting the client, I authenticate the socket connection using JWT.

During the handshake, the backend verifies the token, extracts the authenticated user ID and joins that room automatically.

Any room ID sent by the client is ignored.

Q11. Why not authenticate every socket event?

Answer:

Authenticating every event would introduce unnecessary overhead.

Once the connection itself is verified during the handshake, the socket already belongs to an authenticated user.

That makes every subsequent event trustworthy.

Deployment Questions
Q12. Why couldn't you use Render's persistent disk?

Answer:

The free tier doesn't support persistent storage.

Since uploaded resumes are only temporary until they are parsed and uploaded to Cloudinary, I switched to temporary container storage and deleted files immediately after processing.

Q13. Why upload to Cloudinary?

Answer:

Containers on Railway or Render can restart at any time.

If resumes stayed inside the container, they would disappear after redeployment.

Cloudinary provides permanent storage and CDN delivery.

Q14. Why did React show 404 after refreshing?

Answer:

React Router performs routing on the client side.

When I refreshed /dashboard, Netlify searched for a physical folder called /dashboard, which doesn't exist.

I fixed it by adding a rewrite rule that redirects every request to index.html.

Q15. Why did the build work locally but fail on Netlify?

Answer:

Windows file systems are case-insensitive while Linux is case-sensitive.

My imports used incorrect capitalization. Windows accepted them but Linux rejected them.

After correcting every import and configuring Git to respect case changes, the deployment succeeded.

Q16. Why pin Node.js version?

Answer:

Different Node versions support different JavaScript features.

My dependencies were developed on Node 20, but Netlify was using an older runtime.

Pinning the version ensured the build environment matched my development environment.

Q17. Why use environment variables instead of localhost?

Answer:

localhost only exists during local development.

After deployment every service has a different URL.

Environment variables allow the same codebase to work locally, on staging, and in production without modification.

Bug Fix Questions
Q18. How did you discover the socket vulnerability?

Answer:

While testing I manually emitted a different user ID from the browser console.

I realized the server trusted the client completely.

That showed me the room joining mechanism wasn't secure.

Q19. Why use finally instead of catch?

Answer:

catch only executes when an exception occurs.

I wanted temporary files to be deleted regardless of whether parsing succeeded or failed.

finally guarantees cleanup in both cases.

Q20. What happens if the Python service crashes?

Answer:

Express catches the timeout or network exception.

The temporary upload is deleted inside the finally block.

The client receives an error response, but the rest of the application continues working normally.

Advanced Questions (Product Companies)
Q21. If 1,000 users upload resumes simultaneously, what breaks first?

Answer:

The Python parsing service becomes the bottleneck because parsing PDFs is CPU-intensive.

To scale it, I'd introduce a queue using BullMQ, RabbitMQ, or Celery. Express would return a task ID immediately, background workers would process resumes asynchronously, and Socket.io would notify the frontend when parsing completed.

Q22. If you rebuilt this today, what would you change?

Answer:

Three things:

Make resume parsing asynchronous with a message queue.
Replace regex extraction with an NLP model or LLM-based parser for better accuracy.
Add Redis as the Socket.io adapter so chat can scale across multiple backend instances.
Q23. What is the biggest lesson you learned from this project?

Answer:

I learned that building features is only part of software engineering. The harder part is designing systems that remain responsive, secure, and deployable. Separating CPU-intensive work, securing WebSockets, handling deployment differences between Windows and Linux, and cleaning up resources taught me much more than simply writing APIs.
